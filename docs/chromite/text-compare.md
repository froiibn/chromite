# 텍스트 비교 (Compare, 앱 변경 #105)

## 목적

사용자 요청(2026-11-12): "diff는 주로 쿼리나 프로시져의 차이를 볼때 쓴다", "diff는 버튼을 누르면 열려있는 창을 두개 선택하게 하고 선택된 창의 내용을
비교하는 팝업화면으로 만든다", 팝업을 본 뒤 "그냥 스키마 비교처럼 별도 탭으로 생성하는건 어떤가"(같은 날). 열린 창 두 개(쿼리 창, Modify 창, DDL 탭)의 글을
나란히 놓고 다른 줄과 다른 낱말을 칠하는 **비교 문서 탭**을 연다. 읽기 전용이다.

같은 요청의 "자동 쿼리 포맷"은 이미 있는 Format SQL(Edit > Advanced, Ctrl+K Ctrl+D 또는 Ctrl+Shift+F, 도구 막대 단추)이라 이 작업에 넣지 않았다.

## 화면

1. **비교 단추**: SQL Editor 도구 막대의 Format SQL 바로 오른쪽(아이콘 `compare`: 나란한 두 장, 가운데 줄이 왼쪽 초록·오른쪽 빨강). 같은 동작이
   **Query > 비교**(영어 `Compare…`)에 있다. 도구 설명은 기능 이름 "비교"(앱 변경 #103). 글이 있는 창이 둘보다 적으면 꺼지고 도구 설명 둘째 줄이 이유
   ("비교하려면 쿼리 창이나 DDL 탭을 두 개 이상 여세요.")를 말한다. 단축키는 없다(아래 "설계 결정").
2. **창 고르기**(모달 대화상자 "창 비교"): "왼쪽:", "오른쪽:" 콤보 두 개. 목록은 쿼리 창을 먼저, 다음에 DDL 탭을 탭 순서대로 보이고, 행은 탭과 같다:
   탭 아이콘, 탭 제목(고침 표시 `*` 포함), 제목 안의 연결 이름은 Object Explorer와 같은 연결 색 알약. 처음 값은 왼쪽 = 활성 창, 오른쪽 = 그 전에 활성이던 창
   (없으면 목록에서 왼쪽이 아닌 첫 창). 같은 창을 두 번 고르면 비교 단추가 꺼지고 안내 줄이 "서로 다른 창 두 개를 고르세요."가 된다. Esc는 취소.
3. **비교 탭**: 스키마 비교처럼 문서 탭(`ToolDocument`)이고 명령마다 새 탭이다. 탭 제목 `비교: <왼쪽 창 이름> ↔ <오른쪽 창 이름>`(파일·객체 이름, 연결과 `*` 없이),
   아이콘 `compare`, 도구 설명은 두 창의 탭 제목 전체. 다른 탭처럼 닫고(×, 가운데 단추, 탭 메뉴) 고정·위치를 바꾼다. 다시 시작할 때 복원하지 않는다.
   비교 탭과 다른 도구 탭(스키마 비교 등)은 창 고르기 목록에 나오지 않는다.
   - 도구 막대: 이전 차이(Alt+↑), 다음 차이(Alt+↓), 좌우 바꾸기, 새로 고침 │ 공백 무시, 대소문자 무시, 빈 줄 무시 │ 오른쪽 끝 상태("차이 3곳", "같음",
     "옵션을 켜서 같음(공백, 대소문자, 빈 줄만 다름)", "비교하는 중", 크기 초과 안내).
   - 보기: 좌우 두 칸, 쿼리 창과 같은 구문 색·글꼴·테마, 줄 번호. 칸마다 머리글(탭 아이콘, 탭 제목, 연결 색 알약, 선택 영역이면 "선택 영역, 12–30줄",
     닫힌 창이면 "창이 닫혀 마지막 글을 보임"). 오른쪽 끝에 개요 띠.

## 동작

- **비교하는 글**: 창에 선택 영역이 있으면 선택 영역, 없으면 전체. 선택이 줄 처음에서 끝나면(줄 단위로 고른 경우) 끝 줄은 그 앞 줄로 센다.
  글은 창의 편집기에서 바로 읽는다(저장하지 않은 글 포함). 서버에서 아무것도 읽지 않고 연결·세션·트랜잭션을 건드리지 않는다.
- **줄 맞춤**: 한쪽에만 있는 줄의 맞은편에 빈 채움 행을 넣어 같은 줄이 늘 마주 본다. 채움 행은 줄 번호가 비고 옅은 회색이다. 두 칸은 세로·가로 스크롤이 함께 움직인다.
- **색**: 바뀐 줄과 왼쪽에만 있는 줄은 초록(왼쪽 칸), 바뀐 줄과 오른쪽에만 있는 줄은 빨강(오른쪽 칸), 반투명. 바뀐 줄 안의 다른 낱말은 같은 색을 진하게.
  스키마 비교의 원본(초록)·대상(빨강) 색 그대로다.
- **차이 하나**: 같은 줄로 끊기는, 다른 행이 이어진 묶음. 개수·이전/다음이 이 단위다. 이전/다음은 마지막으로 누른 칸의 커서 기준이고 끝에서 처음으로(처음에서 끝으로) 돈다.
  비교가 끝나면 첫 차이로 간다.
- **옵션**: 공백 무시 = 줄 앞뒤 공백을 무시하고 이어진 공백을 하나로 본다(낱말 표시에서도 공백은 칠하지 않음). 대소문자 무시. 빈 줄 무시 = 공백뿐인 줄은
  짝짓지 않고 차이로 세지 않는다(제자리에 칠하지 않고 둠). 옵션을 바꾸면 바로 다시 비교한다. 줄 끝 문자(CRLF/LF/CR)와 마지막 줄 바꿈은 옵션과 상관없이 차이가 아니다.
  세 옵션은 사용자 설정(Swing 번들 설정 저장소 `textCompare.ignoreWhitespace`, `textCompare.ignoreCase`, `textCompare.ignoreBlankLines`)에 기억한다.
- **같음**: 차이가 없으면 상태가 "같음". 옵션 때문에 같아졌으면(옵션 없이 비교하면 다르면) "옵션을 켜서 같음"이라고 말한다.
- **좌우 바꾸기**: 두 쪽을 바꿔 다시 비교한다(창을 다시 읽지 않음, 탭 제목도 바뀜). **새로 고침**: 두 창의 지금 글(선택 영역 규칙 그대로)과 탭 제목을 다시 읽는다.
  창이 닫혔으면 마지막으로 읽은 글을 그대로 두고 머리글이 알린다.
- 읽기 전용: 병합, 편집, 다른 쪽으로 복사가 없다. 칸 안에서 글을 골라 복사하는 것은 편집기의 보통 복사다(채움 행은 빈 줄로 복사된다).

## 크기와 시간

- 비교는 EDT 밖의 작업(`AbstractJob`)에서 하고, 마지막으로 요청한 비교의 결과만 보인다(앞 비교가 늦게 끝나면 버림).
- 제한: 한쪽이 200,000줄이나 20,000,000자를 넘으면 비교하지 않는다. 두 칸에 글은 보이고 칠하지 않으며 상태가 "비교하기에 너무 큽니다: 한쪽이 200000줄 또는 20000000자를 넘습니다."다.
- 잰 시간(JBR 25, 같은 알고리즘의 단독 실행, 아래 "확인"): 2만 줄에 차이 3곳 14 ms, 2만 줄이 모두 다름 106 ms, 반복 줄(GO/END/BEGIN)을 섞은 2만 줄 0.7 s,
  2,000가지 줄을 무작위로 섞은 2만 줄 두 개(최악에 가까움) 9 s. 마지막 경우에도 화면은 멈추지 않고 상태가 "비교하는 중"이다.

## 설계 결정

| 결정 | 이유 |
|---|---|
| 줄 비교는 모델의 Myers `Diff` 하나, 스키마 비교의 LCS는 지움 | LCS는 줄 수의 곱만큼 표를 만든다(2만 × 2만 = 4억 칸, 1.6 GB). 그래서 4백만 칸을 넘으면 같은 위치끼리 비교해 한 줄이 끼면 그 뒤가 모두 다르게 나왔다. Myers는 차이 수에 비례하고 메모리는 줄 수에 비례한다. 같은 알고리즘이 이미 모델에 있다(CLAUDE.md 4번: 줄 비교 하나) |
| 한쪽에만 있는 줄을 Myers 전에 뺌 | 짝이 될 수 없는 줄이라 결과(최장 공통 부분열)가 같고, 전혀 다른 두 글이 바로 끝난다. 무작위 시험 2만 건에서 짝지은 줄 수가 DP LCS와 같음을 확인 |
| 좌우 맞춤은 채움 행(연결 띠 아님) | 행 수와 줄 높이가 같아 스크롤 맞춤이 값 하나로 된다. 띠는 두 칸 사이에 그리기와 두 스크롤 위치의 대응이 필요하다 |
| 낱말 단위 표시(글자 단위 아님) | SQL은 식별자·키워드·숫자 단위로 바뀐다. 글자 단위는 `user_id`→`order_id`에서 `use`/`orde`처럼 조각이 나 읽기 어렵다. 한 줄 낱말이 5,000개를 넘으면 줄 전체를 칠한다 |
| 색은 스키마 비교 그대로 | 앱 안에서 같은 뜻의 색. 실행 중 문장 색(`Chromite.editor.runningStatementBackground`, 밝은 `#e8f5a0` 연두, 어두운 `#3d4718` 올리브)과 색상이 다르고, 읽기 전용 보기에는 실행 중 표시가 없다 |
| 개요 띠는 직접 그림(`ErrorStrip` 아님) | `ErrorStrip`은 파서 알림만 표시해 칸마다 차이를 알리는 파서를 붙여야 한다. 직접 그린 띠는 60줄 정도이고 왼쪽 반·오른쪽 반으로 두 칸의 차이를 따로 보인다 |
| 문서 탭, 명령마다 새 탭 | 사용자 결정(팝업을 본 뒤 "스키마 비교처럼 별도 탭으로"). 비교하며 원래 창으로 가서 고친 뒤 새로 고침을 누를 수 있고, 비교 여러 개를 탭으로 둔다. 탭의 기존 동작(닫기, 고정, 위치, 여러 행)을 그대로 쓴다. 처음에는 모달이 아닌 팝업(메인 창의 85%)으로 만들었다가 바꿨다 |
| 창 고르기는 콤보 두 개, 창이 둘뿐이어도 물음 | 어느 쪽에 놓일지가 바로 보인다. 늘 같은 흐름이고 좌우를 정할 수 있다 |
| 목록은 쿼리 창과 DDL 탭만 | 둘 다 같은 편집기로 글을 그대로 내준다. Modify·New·Query Library 창은 쿼리 창이다. 디버거의 소스, 테이블 디자이너의 DDL 미리 보기, 스키마 비교 안의 DDL은 창의 글이 아니라 넣지 않았다 |
| 단축키 없음 | 버튼과 메뉴로 충분하고, 빈 키를 차지하지 않는다. 이전/다음 차이 Alt+↑/↓는 초점이 비교 탭 안에 있을 때만 걸린다(탭 패널의 `WHEN_ANCESTOR_OF_FOCUSED_COMPONENT`, 그 탭의 두 편집기는 줄 옮기기 키를 같은 동작으로 덮음). WinMerge의 키이고, 메인 창은 Alt+↑/↓를 묶지 않으며(Query 메뉴는 Alt+PageUp/PageDown, F7은 Object Details), Alt+↓처럼 다른 키와 함께 누른 Alt는 떼어도 메뉴 막대를 고르지 않는다(FlatLaf, 앱 변경 #102의 `AltMouseMenuGuard`는 마우스만 다룸) |
| 비교 탭은 다시 시작할 때 복원하지 않음 | 다른 도구 탭(스키마 비교 등)처럼 복원 기록(쿼리 창만)에 들어가지 않는다. 창의 글을 그때 읽은 것이다 |

## 스키마 비교와 함께 쓰기

`SchemaComparePanel`의 아래쪽 두 DDL 보기가 `TextDiffView`가 되었다. 그대로인 것: 원본 초록·대상 빨강 색, 줄 앞뒤 공백만 무시하는 줄 비교
(`TextDiff.Options.SCHEMA`), 머리글 문구(원본: 연결 / 스키마, 스키마 이름을 대상 이름으로 표시), 한쪽에 객체가 없으면 그쪽에 "(이 스키마에 없음)"과 다른 쪽 전체 칠하기,
비교 전 빈 상태의 두 칸 "(이 스키마에 없음)", 첫 차이로 이동. 달라진 것(보기를 함께 쓴 결과): 좌우를 맞춘 채움 행, 바뀐 낱말의 진한 표시, 스크롤 맞춤, 개요 띠,
비교가 EDT 밖에서 됨, 큰 DDL도 위치 비교가 아니라 실제 비교.

## 넣지 않은 것 (선택 사항)

- Tools > 텍스트 비교(빈 비교 탭에서 양쪽을 고르기), Object Explorer의 "비교"·"다음과 비교…"(사용자 결정 2026-11-12: 단추 → 두 창 고르기 → 비교 탭 하나의 흐름)
- 파일, 서버의 객체 소스(프로시저·뷰·테이블 DDL을 서버에서 읽기), Modify 창의 고친 글과 서버 정의 비교, 쿼리 기록 항목과 비교
- 병합, 편집, 다른 쪽으로 복사, 세 쪽 비교, 데이터(행) 비교(로드맵 6번)
- 비교 결과 내보내기
