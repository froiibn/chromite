# 창을 닫은 뒤 남는 프로세스 (앱 변경 #96)

## 목적

2026-11-12 사내 폐쇄망 PC(인터넷 없음)에서 설치본 0.1.4 위에 26.0.5 설치 프로그램을 손으로 실행했더니 "Chromite가 실행 중"이라며
진행하지 않았다. 사용자가 Chromite를 닫고 [다시 시도]를 눌러도 같았고, 작업 관리자로 프로세스를 끝낸 뒤에야 설치됐다.
닫을 때 Chromite는 데이터베이스에 연결된 상태였다. 인터넷이 되는 다른 PC에서는 닫기만 해도 설치(자동 업데이트)가 진행됐다.

설치 프로그램은 설치 폴더의 `jre\bin\server\jvm.dll`을 쓰기로 열 수 있는지로 실행 중인지 본다(`tools/installer/chromite.nsi` `WaitNotRunning`).
즉 창이 없어진 뒤에도 그 설치본의 JVM 프로세스가 살아 있었다. 이 문서는 무엇이 프로세스를 남기는지 확인한 결과와 고친 것을 적는다.

## 프로세스가 끝나는 방식 (확인한 사실)

- Windows에서 Swing 앱은 `System.exit`를 부르지 않는다. 주 창이 닫히면 `ChromiteSwingApplication.run`이 업데이트 적용(`UpdateService.applyAtExit`)과
  플랫폼 정리(`shutdown`)를 하고 반환하며, Equinox가 프레임워크를 내린 뒤 런처가 프로세스를 끝낸다.
- **데몬이 아닌 스레드는 프로세스를 붙잡지 않는다.** 실행 중인 앱에 끝나지 않는 비데몬 스레드를 넣고 닫아도 0.6초 만에 끝났다(런처가 JVM을 끝낸다).
  그래서 프로세스가 남는 경우는 둘뿐이다: 주 스레드가 `start`에서 돌아오지 않거나(창·대화상자가 아직 기다리는 중, 또는 창이 닫힌 뒤의 단계가 막힘),
  같은 설치본의 **다른 프로세스**가 있다.
- 스레드 덤프는 번들 JRE에 `jcmd`가 없어 `D:\Tools\jbrsdk-25\bin\jcmd`로 앱의 JVM에 붙어 받았다.

## 재현한 경우 (0.1.4 휴대용 zip, 26.0.5 zip, devel 빌드)

시뮬레이션은 모두 JVM 안에서만 했다(방화벽·hosts·어댑터를 바꾸지 않음): HTTPS 프록시를 닿지 않는 주소(`10.255.255.1:81`)나
받기만 하고 답하지 않는 로컬 서버로, 업데이트 확인의 사이트를 그런 서버로(`chromite.update.test.origin`, 개발 빌드),
데이터베이스는 터널 앞의 내 TCP 프록시를 "얼려"(소켓은 열어 둔 채 아무것도 넘기지 않음) 서버가 말없이 사라진 상태로 만들었다.

## 원인 1: 끝날 때 업데이트 확인을 기다림

### 근거

- `UpdateService`는 확인·받기·끝날 때의 적용을 데몬 스레드 하나("Chromite updater")에서 차례로 돌린다. 확인은 창이 열리고 10초 뒤 한 번,
  그 뒤 한 시간마다 돈다(`FIRST_CHECK_MS`, `EVERY_MS`).
- 끝날 때 `applyAtExit`는 적용할 파일을 고르는 일(`toApply`)을 같은 실행기에 넣고 **120초까지** 기다렸다(`EXIT_CHECK_SECONDS`).
  확인이 도는 중이면 `toApply`는 그 확인이 끝날 때까지 차례를 기다린다.
- 사이트에 닿지 않을 때 확인 하나의 길이(`UpdateHttp.fetchFeed`, 26.0.5 클래스로 직접 잼): 닿지 않는 주소 10.0초(연결 시간 제한),
  받기만 하고 답하지 않는 서버 10.0초(요청 시간 제한), 풀리지 않는 이름·거부하는 포트 0초. 이름 풀이 자체는 `HttpClient`의 시간 제한 밖이라
  DNS 서버가 답하지 않는 폐쇄망에서는 운영체제의 이름 풀이 시간만큼 더 걸릴 수 있다(이 PC에서는 재현 못 함).
- 앱에서: 확인이 도는 중(창이 열리고 12초 뒤)에 닫으면 창은 바로 없어지고 프로세스는 7.3초(26.0.5)·7.7초(0.1.4) 더 남았다.
  그동안 주 스레드는 `UpdateService.applyAtExit`(26.0.5 `UpdateService.java:713`, `get(EXIT_CHECK_SECONDS)`)에서, 업데이터 스레드는
  `UpdateHttp.fetchFeed` → `HttpClientImpl.send`에서 기다렸다(덤프 `dumps\u265-b.txt`).
- 업데이트를 끈 경우: 확인을 예약하지 않으므로(`UpdateService.start`, `prefs.enabled`) 이 기다림이 없다(코드 근거, 앱에서는 확인하지 않음).

### 고친 것

- 끝날 때 도는 중인 확인(과 그 안의 받기)을 **멈춘다**: `check`가 자기 스레드를 `checkingThread`에 두고, `applyAtExit`가 `stopped`를 세운 뒤 그 스레드를
  인터럽트한다. `HttpClient.send`는 인터럽트되면 요청을 취소하고 돌아오고, 받는 중이면 `cancelled`로 감시 타이머가 1초 안에 스트림을 닫는다.
  둘 다 받던 `.part` 파일을 지운다(받기를 마친 파일만 이름을 바꾸고, 다음 시작은 받아 둔 파일도 다시 확인한 뒤에만 쓴다).
- 업데이터 스레드가 `toApply`를 **시작**하기를 `EXIT_BUSY_SECONDS`(2초)까지만 기다린다. 시작하면 그 일(받아서 확인한 파일의 마지막 서명 확인)은
  지금처럼 `EXIT_CHECK_SECONDS`(120초)까지 기다린다. 이름 풀이처럼 인터럽트로 멈추지 않는 일이 2초 안에 비키지 않으면 이번 끝에는 적용하지 않고 로그를 남긴다.
- 기다림의 순서: 확인이 시작 전에 `checkingThread`를 세우고 그 뒤에 `stopped`를 읽는다. 끝은 `stopped`를 세운 뒤 `checkingThread`를 읽는다(둘 다 volatile).
  그래서 어느 쪽이든 다른 쪽을 본다. 늦게 도착한 인터럽트는 실행기가 다음 일을 돌리기 전에 지운다(`ThreadPoolExecutor`).

### 지키는 것

- 받아서 확인한 업데이트는 끝날 때 그대로 적용된다. 그 순간 다음 확인이 돌고 있어도(사이트가 답하지 않아도) 적용된다.
- 받는 중이던 업데이트는 적용하지 않고 반쪽 파일을 남기지 않는다. 다음 시작이 다시 받는다.

### 확인 (고친 뒤)

시험 하네스(`D:\Tools\_scratch\exit-leaves-process\harness\ExitHarness.java`, 저장소 밖): 업데이트 클래스를 OSGi 없이 로컬 사이트(127.0.0.1)와
시험 모드 APPLY 자리로 돌리고 `applyAtExit`의 시간을 잰다(도우미는 dry run, 설치 파일을 실행하지 않음). 26.0.5 jar와 새 jar를 같은 하네스로 비교했다.

| 경우 | 26.0.5 | 고친 뒤 | 적용 |

| 사이트가 받기만 하고 답하지 않음, 확인 2초째에 끝 | 8.0초 | 0.0초 | 없음(둘 다) |
| 설치 파일을 천천히 받는 중에 끝 | 0.9초 | 0.0초 | 없음, 남은 파일 없음(둘 다) |

격리 시험 설치본(`INSTANCE=ChromiteTestExit`, 사용자별, `D:\Tools\_scratch\exit-leaves-process\inst`, `Updates: APPLY (installed)`): 0.6초·0.6초.
연결 4개 + 연결 새로 고침 + 다시 연결 + 확인 중에 닫기 0.8초. 열린 트랜잭션과 저장하지 않은 쿼리 창은 둘 다 물었다(저장 안 함 → 롤백 → 끝).
아무것도 없이 닫기 0.6초(느려지지 않음).

## 업데이터에서 보이는 것 (자동 업데이트)

- 도우미(PowerShell)와 앱의 사본은 끝나는 Chromite 프로세스(PID)를 300초까지 기다린 뒤 `setup.exe /S`를 실행한다(`UpdateApplier.WAIT_SECONDS`,
  `UpdateHandOver.waitForOldApp`). 원인 1의 기다림(최대 수십 초)은 이 300초 안이라 자동 업데이트를 실패시키지 않았다.
- 조용한 설치는 `jvm.dll`이 풀리기를 60초 기다리고 종료 코드 2로 끝난다. 같은 설치본의 **다른** 프로세스(원인 2의 두 번째 시작)가 있으면 이렇게 된다.
  그러면 다음 시작에 알림 "업데이트를 설치하지 못함 — 버전 X를 설치하지 못했습니다(코드 2). 지금 버전을 계속 씁니다."가 한 번 보이고,
  그 버전은 그냥 닫을 때 다시 적용하지 않는다([지금 다시 시작]은 다시 시도한다, [auto-update.md](auto-update.md) "적용").
  [지금 다시 시작]의 진행 창은 설치 프로그램의 종료 코드로 실패를 보인다.

## 재현하지 못한 것

- 인터넷 없이 연결된 채 닫았을 때 **몇 분** 이상 남는 경우. 원인 1은 확인 하나의 길이(이 PC에서 10초, DNS가 답하지 않는 망에서는 더 길 수 있음)만큼만
  남긴다. 사용자가 닫은 뒤 바로 [다시 시도]를 눌렀다면 원인 1로 설명되고, 오래 기다려도 남았다면 원인 2(다른 프로세스)나 이 PC에서 만들지 못한
  조건(DNS 서버가 답하지 않음, 연결을 받고 끊지 않는 프록시)일 수 있다.
- 다른 Windows 사용자 세션의 Chromite(같은 설치 폴더를 쓰는 공유 PC, 원격 데스크톱): 여기서 시험할 수 없다. 설치 프로그램의 확인은 세션을 가리지 않는다
  (그 프로세스도 `jvm.dll`을 쥐고 있으므로).

사용자 PC에서 구별하는 방법: 다음에 같은 일이 생기면 (1) 작업 관리자 [세부 정보]에서 `Chromite.exe`/`chromite-swing.exe`가 몇 개인지,
Alt+Tab에 "작업 영역을 잠글 수 없음" 창이 있는지(원인 2), (2) 작업 공간의 `.metadata\chromite-debug.log`에서 닫은 시각 근처에 "Main window closed"와
"(Swing) shutdown completed"가 있는지와 그 사이의 시간(원인 1이면 몇 초 벌어지고, 줄이 없으면 창이 실제로 닫히지 않음)을 본다.

## 범위 밖에서 본 것 (고치지 않음, 보고만)

- 26.0.5: 끝날 때 쿼리 창을 "저장 안 함"으로 닫았는데 다음 시작이 그 창들을 복원할지 물었다(쿼리 창 복원 기능의 의도인지 확인 안 함).
- SQL Server: 받기만 하고 답하지 않는 서버에 연결하면 사전 로그인(`SQLServerConnection.prelogin`)이 190초 넘게 시간 제한 없이 기다렸다.
- Altibase·Oracle: 말없이 사라진 서버의 연결을 닫을 때 드라이버가 읽기 시간 제한 없이 기다린다(Altibase `CmProtocol.disconnect`, keep-alive의 다시 연결 `handshake`).
  끝낼 때는 플랫폼의 끊기 시간 제한 5초와 "실행 중인 작업" 질문이 막는다.
